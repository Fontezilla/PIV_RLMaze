🎯 Introdução

O problema

Contexto — FNR 2026
Festival Nacional de Robótica 2026. O desafio é controlar uma frota de robots AGV (Automated Guided Vehicles) numa fábrica simulada para entregar caixas o mais eficientemente possível.

O que os robots fazem
Cada robot navega autonomamente num grafo de corredores. Recebe caixas num nó de entrada (entry), transporta-as por estações de processamento opcionais, e entrega-as em nós de saída (exit).

O objectivo do agente RL
Minimizar o tempo total de entrega de todas as caixas — ticks_to_all_done. Não basta entregar; tem de entregar depressa, sem deadlocks, e usando todos os exits de forma equilibrada.
O que o agente decide
A cada evento (robot livre, caixa entregue, novo spawn), o agente recebe o estado e decide — para cada robot pendente — qual caixa pegar e para qual exit levar:
assignment: (box_id, exit_node) | None
O routing de baixo nível (como chegar lá sem colidir) é tratado pelo Router com A* + sistema de locks. O agente não se preocupa com isso.

Abordagem
GNN heterogéneo (SAGEConv) que codifica o estado da fábrica como um grafo, seguido de PPO com GAE para aprender a política de scheduling.

Como funciona physics.tick(robot)

Velocidade adaptativa por zona:
O robot abranda antes de entrar numa curva (progress próximo de 1.0, próximo nó é curva) e depois de sair de um dead-end (progress próximo de 0.0).

Turn delay:
Quando um robot chega a um nó e vai virar ≥ 45°, wait_ticks é definido a 3 ou 5. O robot fica parado esses ticks antes de começar a mover para o próximo nó.
# progress por tick:
delta = speed / edge_distance
progress += delta

# velocidade-alvo:
if parked_at: target = V_CURVE
elif dead_end: target = V_REVERSE
elif in_curve_zone: target = V_CURVE
else: target = V_STRAIGHT

# aceleração suave:
speed = clamp(speed ± ACCEL, target)

Nas fases de processo, a constraint é um par [entry, exit].
Quando o robot dropa em pX_entry:
— A caixa reaparece em pX_exit imediatamente
— O robot fica livre no mesmo tick
— O agente recebe +1.0 (waypoint reward)
— A caixa passa para a fase seguinte da pipeline

apply_sequential() — masking sequencial

Para cada robot pendente, por ordem:
  1. Calcular logits sobre todos os candidatos
  2. Mascarar box_id já atribuído → -∞
  3. Mascarar drop_node já tomado → -∞
  4. Mascarar idle se há algum candidato válido → -∞
  5. Sample / argmax / log_prob consoante o modo
  6. Actualizar assigned_boxes e assigned_nodes para o próximo robot

Extra features dos candidatos (CANDIDATE_EXTRA_DIM = 3)

FeatureCálculoRange
n_robots_at_target n_robots no nó alvo / MAX_ROBOTS_PER_NODE (4) [0, 1]
is_someone_goal 1.0 se algum robot tem goal_node == target {0, 1}
in_future_path 1.0 se target aparece no future_path de algum robot {0, 1}
Estas 3 features passam por W_extra: Linear(3 → hidden_dim) e são somadas ao embedding do candidato antes do scoring. Permitem ao agente aprender que enviar dois robots para o mesmo nó é sub-óptimo — sem hard mask.

Diferença is_idle() vs is_free()
is_idle() — só verifica o state. Um robot pode estar IDLE mas ainda ter assigned_box_id (a caminho de um pickup).

is_free() — verifica state + sem cargo + sem reserva. Usado pelo env para saber se o robot pode receber um assignment de raiz.
idle_acknowledged
Quando o agente diz None (idle) para um robot, idle_acknowledged=True é activado. O robot não é re-perguntado até que haja nova informação no mundo (novo box spawn, pick, etc.).

Congestion cache — 1× por robot por tick

Sem cache, build_future_edge_usage() seria chamado em cada replan e alt_plan dentro do mesmo tick — até 2× por robot. Com o cache:
begin_tick() → _congestion_cache.clear()
_congested_edges_for(robot)
  # hit? → retorna cached
  # miss? → computa, guarda, retorna
Resultado: build_future_edge_usage chamado no máximo 1× por robot por tick, independentemente de quantas vezes o router replana.

Sistema de prioridades dinâmicas

_update_priorities() corre cada tick para todos os robots.
A prioridade é usada pelo router para decidir quem cede: um robot com prioridade maior nunca parka para ceder passagem a um com prioridade menor.
if carrying_box is None:
  priority = 0.0
else:
  progress = steps_done / total_steps
  priority = 1.0 + 0.5 × progress

GAE — bootstrap por tipo de terminação

TipoCausanext_value
terminated all_delivered() = True 0.0 — estado terminal real
truncated tick ≥ tick_limit V(s_T) — bootstrap com critic
# _compute_gae — por segmento de episódio:
if last_t.terminated:
  next_value = 0.0
else: # truncated
  next_value = critic(last_t.graph)

gae = 0.0
for i in range(end, start-1, -1):
  δ = reward_i + γ × next_value − V_i
  gae = δ + γ × λ × gae
  advantage_i = gae
  return_i = V_i + gae

Sincronização de workers

Por batch (a cada 3 episódios):
1. Main serializa policy.net.state_dict() → CPU
2. Envia via executor.map() para os 3 workers
3. Cada worker: policy.load_state_dict(sd) + run_episode()
4. Trajectory (list[Transition]) retorna ao main
5. Main combina (3 trajectories) → policy.update()

Workers são persistentes:
Env e Policy criados 1× por worker via initializer=_init_worker. Cada episódio apenas re-carrega o state_dict (rápido) e faz env.reset().
